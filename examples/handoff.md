# 示例：原执行者从定位做到验收

以下为虚构场景，不是客户记录或实际性能数据。

用户同时报告“导出缺少单位列”和“搜索清空后列表没有恢复”。主调度保留用户原话并交车道经理；经理为独立问题分别启动执行者甲和乙，在各自工作树中完成定位、修改、验证和清理，不按阶段重新派人。

甲修好源码并通过相关测试后，直接核目标平台运行程序身份，继续实际导出和保存后新进程回读，不把源码阶段交给经理核收再续派。乙继续处理搜索问题；甲需要桌面焦点而用户正在使用时，只调整相应动作，按实时脚本选择获准机器，原线程继续。

甲达到本题验收终点后，保存最终结果、证据和剩余发布步骤，再通知车道经理。记录为“待发版”，列出候选身份与验证层级；这不等于已经发布或用户已验收。发布执行者须在已有授权内完成集成、发布和公开回读，回读通过后才记已完成。

若中途需要用户决定，经理经主调度立即实际呈现问题、推荐和代价。在已经采用约定且宿主允许时，普通决定呈现后 3 分钟未回复按推荐；发布、云端部署、客户和公开数据写入、永久删除、凭据及权限变化仍须明确授权。缺原案材料则登记证据请求，用现有材料完成可做部分并注明原案未覆盖。

需要继续时恢复甲或乙原线程；只有工具证实无法恢复才登记继任。如果车道经理退出，只转交协调责任，不把原执行者换掉。继任协调者核最后回执、实际工具状态和依赖触发，不重复已通过的修复，也不把同一用户目标拆成更多任务。
