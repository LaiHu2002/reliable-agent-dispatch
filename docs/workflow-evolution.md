# 这套多机多代理工作流是怎样形成的

在 APlus 开发中，我们让多个 AI 代理分工修改代码、编译，并在 Mac 和 Windows 上操作 SketchUp 验证结果。负责人希望日常只与一个主调度沟通：提出产品问题、补充现场信息、作必要决定，其余工作由主调度组织。

最初主要由 Claude 做主调度，负责人觉得协作比较顺畅。后来原有使用方式中断，需要让 Codex 接续。迁移让一些原来靠对话习惯维持的配合暴露出来：执行者已经交付，下一步可能没人接；负责人讨论一个新想法，主调度可能答完就结束；机器有空闲，任务却没有合理分过去；长时间没有回应，负责人还得回来确认是否在工作。

这些规则就是在反复使用、追问和修正中形成的。下面按问题的演进讲述，其中几项改进在实际使用中交叉进行。工具名称用于交代背景，文中的体验来自这一个团队。

## 1. 从“执行者完成了”到“交付有人接”

并行以后，每条执行线都会报告进展，但局部交付与整个用户问题结束之间仍有很多工作。源码修改和测试通过以后，可能还要构建新程序、在目标机器上操作、保存重新打开、进入组合版本，最后由用户按原操作验收。

负责人经常需要问：这条已经交出来了，为什么还没继续？如果只看每条代理的结束通知，各自似乎都有结果，真正的用户问题却可能停在两个阶段之间。

于是我们把任务状态明确下来，记录谁正在执行、谁已经交出结果、哪些事情等待主调度处理。现有队列包含排队中、执行中、待主调度处理、等待外部输入和已收尾。执行者保存交付以后，任务进入待主调度处理；“已交付”说明执行者交出了一个阶段的成果，下一责任转到主调度。

交付带上实际结果、证据、剩余工作和具体下一步。主调度检查后，要真正恢复原负责人、交给明确继任者，或说明具体排队与外部缺口，然后确认这条交付已经处理。简单回复“收到”不算安排了下一步。

这个设计也有了程序支持。本地队列分别保存登记、交付和处理记录，当前状态从这些记录恢复。执行者只写自己的交付，主调度负责分派和确认。检查工具能够指出未确认交付，以及执行者已经结束而队列仍写执行中的不一致。任务恢复时先读这些记录，避免把已经通过的阶段重新做一遍。

我们没有在这个公开仓库中附带队列实现，但把交付、确认和恢复所需的信息保留在技能与模板里，便于其他团队对照自己的执行系统。

## 2. 结束前检查仍然会留下一个时间上的缺口

下一步是要求主调度每次结束回复前检查：有没有新交付、哪些执行者已经结束、还有没有可执行工作没有接上。负责人追问进度或临时换话题后，也要回到原来的任务记录。

真实使用中又出现了这样的场景：子代理还在执行，负责人和主调度讨论新的产品想法。主调度把讨论结论输出完，就结束当前一轮。稍后子代理完成，结果仍然没有被主调度继续处理，负责人过一会才发现工作又停了。

这里要核对两种情况。交付在主调度回复结束前已经到达，却没有被检查处理，说明结束前要求没有被执行。如果检查时执行者还在工作，而交付发生在回复结束以后，当时的检查可以完全正确，后来仍然需要有机制让主调度再运行一次。

状态记录让工作留得下来。主调度何时读取这些记录、如何继续执行，还需要分别落实。这个区别后来直接影响了巡检的设计。

## 3. 先试独立定时任务，再把巡检放进主调度自己的代理体系

为了解决回复结束后的漏接，负责人专门建立过一个每十分钟执行一次的定时任务，希望它查看任务记录，发现有交付等待处理时发送提醒。

按负责人对这次尝试的回顾，关键困难是通知归属：独立定时任务无法确定该把提醒送入哪个主调度对话。检查虽然可以按时发生，结果却没有顺畅地回到负责这批工作的主调度。

随后，负责人把建立巡检的要求写进技能：一个对话只要接任这批工作的主调度，就要为这批工作建立一个低成本巡检子代理。可以选择 Luna 等低成本模型，或按任务使用合适的思考深度。巡检与当前主调度关联，读取同一批任务记录，并通过现有代理消息通道报告异常。

这次调整把三件事放到了一起：巡检看哪批任务、报告给谁、通过什么通道送达。负责人观察到，这样能够更有效地把遗漏交付交回对应主调度。

巡检后来也需要细化职责。它只检查有证据的调度缺口，例如交付是否久未处理、执行者已经结束而记录仍写运行、是否有可执行任务无人负责。它不接管队列、不替主调度改派任务，避免同时出现两个调度指挥同一批工作。

提醒也要依据最新状态。主调度可能已经接续了一个旧事件，执行者的历史完成正文也可能与当前运行状态不同。巡检如果只读旧记录，会把已处理的事情再次报成遗漏。因此我们补了读取当前代理状态、核最近回执和避免重复提醒的要求。健康状态不反复报平安；主调度处理后，再返回实际处置结果。

目前这套巡检依赖所用工具的投递与运行能力。在活动主调度内送达提醒的结果，可以直接记录；停止、关闭或应用重启之后能否恢复，还要分别验证。十分钟是本团队的使用选择，周期也要考虑占用一个代理名额和每轮推理的成本。

## 4. 子代理自己选机器，出现了局部拥堵和整体空闲

多机开发初期，子代理可以自行选择在哪台电脑执行。每个代理只看到自己当前的任务和部分资源，难以知道其他执行者接下来会使用哪台机器。

负责人需要使用一台电脑时，会告诉主调度这台暂时不能接任务。多个子代理可能同时转向另一台电脑。等负责人用完，再说这台可以恢复工作，主调度有时只把消息写进交接文档，并建议尽量把任务分过去。多个执行者看到同一个可用消息，又一起涌向刚恢复的机器。

这样虽然有多台 Mac 和 Windows，任务仍会集中在少数机器上，其他容量没有充分用起来。负责人还要不断观察哪台太忙、哪台空着，再回来提醒调整。

负责人于是去寻找多机资源监控工具，并把实时查询放进分配流程。现有记录中保留了 Glances 的试用经历；试用组合出现 CPU 总占用异常为零后，当前查询入口改用系统计数和 psutil 等已有能力取得采样。工具选择也需要核对数据是否可信。

更关键的职责调整是：主调度统一查询获准机器的当前资源，结合任务适配性和已派工作，逐项指定每一步在哪台执行。执行者按分配工作，遇到指定动作失败时报告，由主调度决定是否换机。机器暂停或恢复使用以后，主调度逐项调整任务，避免用一条广播让所有执行者整体迁移。

主调度还要计入刚派出、尚未启动的任务。如果只看每次查询时的空闲快照，连续派单仍可能把多个重任务放在同一台暂时空闲的电脑上。

我们也逐渐把几类约束分开：代理名额、每台机器自己的内存与负载、共享文件写权，以及真正需要鼠标键盘的桌面焦点。某台机器的前台被占用，只影响冲突步骤；其他机器和不需要前台的工作继续。具体容量随负载和隔离能力变化，不把一次历史并发数量当成所有机器的通用限制。

## 5. 主调度还必须让人愿意持续和它合作

迁到 Codex 以后，负责人也遇到了沟通方式的问题。有时主调度长时间没有回应，有时回复堆满内部编号和过程，负责人仍然不知道产品问题解决到了哪里。还有一种情况是：它认真回答了最新讨论，却没有继续接住原来并行执行的工作。

为此，负责人又和 Claude 讨论，请它总结主调度怎样与人配合得更顺畅。随后，这些总结被整理进项目的调度技能与反馈流程。现有修改记录能核到及时回应、长任务沟通和先接续后完整汇报的补充。

第一条要求很朴素：“先回一句，再干活。”看到新消息先回应，说明已经知道什么、还要查什么，再去读状态、调用工具和派工。负责人无需在一段沉默里猜测请求是否被接到。短答之后继续调查和执行，不能把这句回应本身当成交付。

第二条是工作期间保持可见。在原实践中，负责人希望持续工作时通常不要超过一分钟没有回应。有新结果、方向变化或阻塞就简短说明；等待时说清等待对象和下一检查节点。这个节奏是双方协作偏好，目的在于让负责人掌握变化，也避免没有事实更新时反复报相同状态。

第三条是按用户问题汇报。第一句说明用户能看到的结果和当前缺口。多项工作按“问题、当前结果、还差什么”列出；分支、进程和详细日志放证据。负责人可以直接判断哪些能用、哪些还需要验证，而不用先翻译内部代号。

第四条是让状态词有实际含义。已经派出、正在执行、源码候选、真实操作通过、已经发布、用户验收分别说明。调用工具准备执行，不能提前说正在执行；测试通过也不能代替负责人或原反馈人的验收。预计时间需要有依据，暂时无法估计就给下一检查节点。

第五条是补充信息只让负责人解释一次。用户把新参数、模型或决定告诉主调度后，由主调度判断属于哪条任务，传给原负责人，更新记录。执行者需要材料或决定时，也由主调度集中沟通，避免负责人在多个会话之间反复转述。

第六条是讨论与执行同时维持。负责人讨论一个新想法时，可以先把想法说清楚；这个新想法只获讨论授权时就保持讨论范围。原来已经授权的任务继续推进，直到负责人明确暂停、取消或调整目标。回答最新消息以后，要回到原来的交付与接续，避免一次讨论把整批工作带到无人照看的状态。

最后，常规技术安排和机器分配由主调度判断，已有授权不反复变成审批；真正会改变业务结果的决定再向负责人集中说明。收到执行者交付后先核必要证据并落实下一步，再作完整汇报。负责人不应因为调度写完了一段总结，又承担起逐条催办的工作。

这些规则已经提炼进[技能入口](../skills/reliable-agent-dispatch/SKILL.md)和[沟通说明](../skills/reliable-agent-dispatch/references/communication.md)。它们来自具体使用中的摩擦；其他团队可以按自己的交流习惯调整节奏和格式。

## 6. 桌面软件让“已经完成”有了更多实际条件

APlus 的任务要进入真实 SketchUp 场景。代码和单测以外，还要确认运行程序包含当前候选，操作使用了正确输入，目标平台能够实际完成对应动作。涉及持久化时，保存后在新进程重新打开，才能检查结果是否留下来。

因此，我们将源码、构建、所需平台实际操作、集成、发布和用户验收分别记录。每一项只要求与用户结果相关的层级；某个平台无法验证时说明具体缺口，其他可执行部分继续。自建场景可以帮助理解机制，覆盖不到原始现场时保留原案验收的欠账。

这些划分也影响调度。一个执行者交付源码候选以后，主调度要知道接下来缺的是产物、目标平台、真实输入还是用户确认。阶段结束时留下明确负责人和下一步，才便于后续接续。

## 7. 我们想带着这些过程交流什么

看到 DeepSeek Super-agent 的设计与公开原型，我们在持续任务归属、独立执行、交付和减少人工盯单方面找到了许多相近问题，也看到职责划分上的不同，详见[原型对照](superagent-comparison.md)。

我们尤其想讨论：哪些规则可以靠技能帮助模型遵守，哪些需要由程序保证；多个人机对话同时存在时，巡检与交付怎样准确回到对应主调度；代理运行能力与真实机器资源怎样协调；怎样判断实质进展，同时让产品负责人保持顺畅沟通。

这些改进仍在使用中继续发生。公开出来，是希望别人能看见每次调整的原因，复用其中有效的做法，也指出我们还没看到的问题。
