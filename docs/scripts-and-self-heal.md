# 规矩写成脚本，机器自己兜底：多代理调度第三版

第二版把经理改成了公共设施，一个问题交给一个执行者做到底。之后又跑了五天，目标也变了：从“用户看着能跑”，变成“用户去睡觉，系统自己连续跑”。

这五天里，我们一边按这个目标改，一边发现了一件更难受的事：拖慢我们的，大多不是产品本身的缺陷，而是我们自己加的规矩。

这篇讲四件事：

1. 卡点都从哪来；
2. 怎么把规矩变成脚本；
3. 机器怎么分配才不浪费；
4. 出了事怎么让系统自己兜底。

## 先说结论

- **限制性的规矩要能指到用户原话。** 对不上原话、也不护着硬边界（发版、云端部署、客户和公开数据、凭据、权限、永久删除、关机）的门槛，删掉或降成只记录。新加门槛和产品里加路障一样，要用户单独批准。
- **能写成脚本的规矩写成脚本，不靠记得。** 条文在长对话里触发不稳定；命令行上的硬检查要么拒收，要么报红。经理的大部分活也是这样被换掉的。
- **机器按实时压力放行，不按账面预约。** 先放进去，预约跑起来以后按实测纠正；真过载了，再把最新放进去的任务退回池子。
- **我们拦不住模型写出坏脚本，但能把自愈做好。** 失控进程由每台机器本地的看门狗掐掉，不靠远程，不等人。
- **每次摩擦都记账。** 要用户介入、有活却空等、同类手工步骤第二次出现，都是摩擦。碰到的人当轮记一行，优先写成脚本消掉。

## 一、卡点从哪来

用户的原话是：“感觉一堆卡点呢，之前没限制都没这么多事。”“感觉规矩都不是我说的，都是你要么 GPT 自顾自加上的，过度防御了。”

我们把一天多的会话记录按卡点分了类：117 条车道，3383 条消息。

| 卡点 | 车道数 | 消息数 |
| --- | ---: | ---: |
| 测试账号轮流用：一场独占一个号，用完“具名交接”给下一顺位 | 63 | 724 |
| 编译等待 | 65 | 660 |
| 机器预约排队 | 65 | 432 |
| 授权链、旧队列、登记回执 | 73 | 277 |
| 审查、复核（例：两行状态元数据也开独立审查） | 48 | 238 |
| 界面锁、前台核对 | 29 | 131 |
| **真实产品缺陷（这才是该干的活）** | 66 | 322 |

真正的产品缺陷只排第四。排第一的“测试账号独占”，是代理自己加的：没人试过同一个账号能不能两处同时登录，就默认不能，于是写出了一整套顺位和交接。后来真试了一次，两台机器同时登录同一个测试账号，两边都有效，互不干扰。这条规矩当天就删了。

另一个例子是写规矩的 AI 自己。用户说过“让小 Mac 多干活”，规矩里却写成了“主力 Mac 不派编译和测试”。用户的更正很直接：“我什么时候说主 Mac 不派编译和测试了，我说的是四台机器都用起来。”

### 做了一次减法

对每一道门槛问两个问题：能不能对到用户原话？护不护着硬边界？两个都答不上的，直接删或降成只记录，不逐条问用户；拿不准的，一条一行带推荐交用户定。

结果：取消 12 道，降级 3 道，保留 16 道。没有一条需要用户另外决定。

### 教训

- 把用户“让谁多干”的话写成规矩时，很容易顺手写成“别人不许干”。限制性的规矩必须能指到原话。
- 代理加门槛几乎没有成本，删门槛却要有人专门去查。所以新增门槛必须过用户这一关，现有门槛定期按上面两个问题过一遍。

## 二、规矩写成脚本

第二版的规矩大多是文字，执行全靠代理记得。长对话一压缩，最先丢的就是这些条文。现在的做法是：凡是能写成检查的规矩，写进命令本身。

- **缺了就拒收。** 改状态的命令缺必填字段直接拒绝，比如“等你定”必须带推荐，“已完成”必须写结果，“已发版”必须带一份写着这个版本号的发布回执。
- **没做就报红。** 定时检查发现通知超过 5 分钟没送到、硬审批没人回、机器闲着却有车道在等，就非零退出，主调度醒来第一件事就看到。
- **条文和脚本冲突时以脚本为准。** 改规矩先改脚本和测试。

经理的活也一件件换成了脚本：

| 原来靠经理 | 现在 |
| --- | --- |
| 看哪些车道该开工、该唤醒谁 | 补位脚本列出全部可开工项，按原负责人分组，附一张开工单（只有用户原话、原件路径和编号）。补位员照着开，开工单原样交给执行者，不改写、不转述 |
| 盯谁卡住了 | 卡死脚本每 15 分钟增量读一遍会话记录，数出“说了下一步、2 小时没下文”“连续 3 次失败”“多条线卡在同一类”“性能线 4 小时没出数字”。巡检每小时只读这份报告，判断根子和该谁动 |
| 分配机器 | 分配脚本，见第三节 |
| 已知故障的处理 | 自愈手册，见第四节 |

经理只剩一层，叫补位员：不跟用户说话，不审查，不读过程。主调度仍是用户唯一的联系人。

还有一条：新角色出现之前，先问它的活能不能写成脚本。

## 三、机器怎么分配

我们有四台机器：一台主力 Mac、一台 16G 内存的小 Mac，加上用户自己也在用的一台 Windows 台式机和一台 Windows 笔记本。

### 现象：小 Mac“一直内存不够”，可它其实很闲

一晚上的记录显示：

- 进等待名单的 25 次申请里，24 次申请的是 Mac。其实很多是 Rust 测试、前端编译、Python 单元测试，根本不依赖 Mac，只是习惯写了 Mac。
- 小 Mac 整晚内存压力正常，实际空着 9 到 11G，CPU 大多在 1% 左右；可账面余量只剩 2G 左右，三个只要 0.25 到 0.5G 的小测试都排不上。
- 原因是预约按“峰值”硬扣，预约了不用也照扣。实测里，SketchUp 实测预约 3G，249 个采样的峰值只有 1.71G；Python 测试预约 0.25G，实际只用 0.02 到 0.05G；前端编译预约 1G，实际 0.03 到 0.28G；Rust 编译峰值 7 到 8G，但只出现在链接那一小段。

### 一次排队死锁

一天夜里，小 Mac 内存空着八成，等待名单却挂着 14 条。三件事叠在了一起：

1. 有一条“大任务等超过 20 分钟，就为它空着一台机器”的保护规则，也是代理自己加的；
2. 被保护的那个任务申请了 9G（同类实测 p90 约 2.6G）。小 Mac 只有 16G，又被一份 7G、实际只用不到 1G 的发版预约占着，而发版预约不缩。这个任务永远放不进去，别人也进不来；
3. 调度会话中断重启后，旧会话留下的等待项每 15 分钟被叫醒一次，没人来领，也永远不退出名单。

### 现在的规则

用户的说法是：“我们就贪心算法呗，你先塞，实在导致这个机器不好了，再把那个任务放到池子里。”“你不干起来，你也不知道。”还有一句：“Mac 有智能的压缩……我的 Mac 开了十几个 SketchUp 也不卡。根本都不需要任何排队。”

- **按实时压力放行。** Mac 只要内存压力不是“严重”就放：macOS 会自己压缩内存，空闲时程序占得多，不代表机器挤。Windows 承诺内存不到 95% 就放；它的承诺内存是硬上限，超了程序直接分配失败，所以这条线要留。
- **平时不排队。** 能放的机器里有一台在线内就当场给，四台都越线才排队。不为任何等待项预留机器。
- **预约按实测纠正。** 开跑满 10 分钟后，预约改成最近 10 分钟峰值的 1.3 倍，最少 0.5G，涨了也跟着调。发版预约同样纠正，只在排先后和退回时保留优先。
- **持续严重过载才退回池子。** Mac 压力严重、或 Windows 承诺内存 ≥ 97%，持续 2 分钟：先暂停后台活，再一次退回一个最新放进去的普通编译或测试，按原排队时间回池。SketchUp 实测最后退，退之前先保存现场。
- **平台无关的活申请“哪个平台都行”。** 小 Mac 放不下就去 Windows 或主力 Mac。
- **叫醒两次都不来领的等待项，移出名单。** 会话停了就别占位置。

这套做法在 [Kubernetes](https://kubernetes.io/docs/concepts/configuration/manage-resources-containers/) 里有现成的对应：按 requests 调度，按 limits 和[压力驱逐](https://kubernetes.io/docs/concepts/scheduling-eviction/node-pressure-eviction/)。我们是在吃了上面这些亏以后才对上号的。

## 四、出了事，机器自己兜底

用户说：“就一个 PowerShell 直接把我们一个机子就干死了……我们不能阻止大模型，或者说阻止你干出这些事情，但是我们把我们自己的自愈做好。”

### 发生了什么

- 笔记本上，一个代理经 SSH 远程起的 PowerShell 脚本，私有内存涨到 56.6G，承诺内存顶到 100%。CPU 只用了 7%，整台机器却一个新任务都接不了，持续了约 1 小时 40 分钟。
- 结束它以后没几分钟，台式机上又起了一个同样的，8 分钟涨到 11.3G。
- 回头一查，台式机 30 天里有 8 次内存耗尽，全是我们自己的 PowerShell，每次 40 到 53G。

### 自愈手册

已知故障由脚本直接修，随每 15 分钟的机器检查运行。现有条目：

- Windows 登录会话泄漏或内存吃紧 → 自动重启。有我们的编译或实测在跑时先等它们收尾；用户登记在用的机器不重启；重启前在屏幕上提示 5 分钟。
- 远程复用连接连不上 → 关掉旧连接，下次采样重开。
- 界面锁过期不还 → 收回。
- 定时检查结果过旧 → 重跑定时任务。
- 我们远程起的 PowerShell 私有内存超过 8G → 先再核一次是不是同一个进程，再结束它并通知。这一轮不重启。

每条修复都要回答三个问题：怎么认出来、怎么修、怎么算修好了。同一问题 6 小时内修 3 次还不好，就交主调度查根子。

主调度或巡检碰到新故障时，可以自己往手册里加规则。新规则先只记录不动手（observe）满 24 小时，再拿事故时刻和正常时刻各回放一遍：事故时刻要命中，正常时刻不能命中，确认没有误报才转正。删除、关机注销、停别人的进程、对外写、凭据、提权这几类动作，手册校验时直接拒收。

### 远程兜底不够，要本机看门狗

15 分钟一次的远程检查有两个洞：

- **太慢。** 每分钟涨 1.4G 的进程，十几分钟就能顶满一台 32G 的机器。
- **最需要的时候用不上。** 承诺内存顶满时，连新的 SSH 会话都可能起不来。

所以下一步是每台机器装一个本机常驻的看门狗：每 15 秒查一次，只认“我们的”进程（经 SSH 起的、我们的计划任务起的、分配脚本登记过的），超线就在本机直接结束，用户的应用一律不碰。Windows 还有现成的[作业对象（Job Object）](https://learn.microsoft.com/en-us/windows/win32/procthread/job-objects)，可以给一整棵进程树设内存硬上限，由系统直接执行。这一节写的时候还在做，没有结果。

## 五、摩擦账本

目标是无人值守持续运行，所以“摩擦”有了明确的定义：

- 要用户本人介入；
- 有活却空等超过 15 分钟；
- 同类手工步骤第二次出现；
- 流程让已有产出作废。

碰到的人当轮记一行：现象、代价、根因、怎么消掉、状态。消掉的方式优先是脚本检查或自动处理，规矩文字只留一个指针。复发了就把状态改回“部分”，不新开重复行。

上面几节的改动，几乎都是从这本账里来的。

## 六、效果和还没验证的

- 规矩减法、分配规则和自愈规则都是这几天才落地的，到写这篇时还没有满一天的对比数据。我们打算跑一天以后，按同样的分类再数一遍卡点，并看同时在跑的任务数、平均排队时间、因过载退回的次数。
- 一次空闲统计显示，四台机器 6 个多小时里 CPU 平均只有 7% 到 22%。机器远没跑满，卡在别处的比卡在机器上的多。所以先把规矩和分配理顺，再决定要不要加机器。
- 所有数字都来自我们本机的会话和资源记录，是实际观察，不是受控实验。

## 七、和第二版相比改了什么

| 第二版（11-13） | 现在 |
| --- | --- |
| 规矩主要是文字，靠代理记得 | 能检查的写进命令：缺了拒收、没做报红；条文和脚本冲突以脚本为准 |
| 车道经理接住、恢复、转达 | 补位员照脚本给的开工单开工；卡死由脚本数、巡检判断；经理只剩一层 |
| 机器用脚本查实时负载，按预约扣余量 | 按实时压力放行，平时不排队；预约跑起来按实测纠正；持续严重过载才退回 |
| 没有专门的自愈 | 自愈手册加新规则先观察再转正；失控进程本机掐掉 |
| 门槛按需添加 | 新增门槛要用户批准；对不到原话、不护硬边界的删掉 |
| 关键路径卡住 15 分钟必须动 | 保留，并扩成摩擦账本：要用户介入、空等、重复手工、产出作废都记 |
