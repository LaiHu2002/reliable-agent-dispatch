# 规则与成熟概念对照

> 本文保留第一版规则的概念对照；协调结构、文件并改和经理容量以[第二版](coordination-structure.md)为准。

[English](en/concept-map.md)

本技能里的大多数规则，在分布式系统、运维和工程管理中都有成熟的对应概念。我们在实践中先遇到问题、后写规则，事后才对照到这些名字。列出来有三个用途：

1. 熟悉这些概念的读者能更快理解每条规则在做什么；
2. 需要把规则落实成程序时，可以直接参考这些领域已有的实现；
3. 说清楚多代理调度和传统场景**不一样的地方**，这才是本仓库主要想补充的内容。

对照只表示“机制相近”，不表示等价。表中的成熟做法也不是本仓库附带的实现。

## 交付与接续

| 本技能的规则 | 相近的成熟概念 | 多代理场景特有的地方 |
| --- | --- | --- |
| 执行者先保存交付，再通知经理 | 事务性发件箱（transactional outbox）；先持久化再发消息 | 代理会在“写完总结”后就结束；通知发出不等于对方被唤醒 |
| 落实下一步之后才确认交付；回“收到”不算 | 消息确认（ack）、至少一次投递、处理完成后再 ack | 消费者是模型，它可以只在文字上确认，而没有实际启动下一步，所以要把“已接续”的证据和确认绑在一起 |
| 同一任务只有一位经理消费交付 | 单一活跃消费者（single active consumer）、独占消费 | 换会话、换模型接任时，旧调度可能还活着，需要显式交接 |
| 旧台账写“执行中”不能证明仍在执行 | 心跳与租约（lease）；过期状态检测 | 代理退出后没人写“已结束”，记录和实际状态常常不一致 |
| 巡检只报有证据的缺口、去重、健康时安静 | 对账循环（reconciliation loop，如 Kubernetes 控制器）；告警去重与抑制 | 难点在于“提醒送进哪个对话”，即通知归属；定时任务本身不难 |
| 交接只留一份当前摘要，写清未消费交付和恢复触发 | 交班交接清单（shift handover） | 继任者往往是一个没有上下文的新对话，只能依赖记录 |

## 归属与资源

| 本技能的规则 | 相近的成熟概念 | 多代理场景特有的地方 |
| --- | --- | --- |
| 同一文件同时只有一个写入负责人 | 单写者原则（single-writer principle）；代码所有权（CODEOWNERS） | 独立工作树会让人误以为可以同时写同一文件 |
| 资源统一分配，计入已派出、尚未启动的任务 | 调度器的资源预留（如 kube-scheduler 在绑定前先把 Pod 记入缓存） | 多个代理读同一份“空闲”消息会一起涌向同一台机器，属于惊群（thundering herd） |
| 代理名额、机器负载、文件写权、桌面焦点分开核算 | 多维资源调度；互斥锁按资源粒度划分 | 桌面 GUI 焦点是独占资源，只能串行，也是传统 CI 很少遇到的约束 |
| 用户只对接主调度，补充信息只解释一次 | 事件指挥体系中的指挥官与单一联络人（incident commander / single point of contact） | 执行代理之间不共享上下文，主调度不转达，信息就丢了 |

## 规模与流程

| 本技能的规则 | 相近的成熟概念 | 多代理场景特有的地方 |
| --- | --- | --- |
| 主调度 → 经理 → 执行者，按积压而不是按部门分组 | 管理幅度（span of control）；Erlang/OTP 的监督树（supervision tree） | 瓶颈是主调度的上下文和单轮处理带宽，不是执行者数量 |
| 经理容量把排队、待验证、外部等待都算进去 | 看板的在制品限制（WIP limit）；利特尔法则（Little's law） | “交出源码就腾出名额”的错觉在代理上特别常见 |
| 状态分级：源码 / 构建 / 平台实操 / 集成 / 发布 / 用户验收 | 完成的定义（Definition of Done）；持续交付的部署流水线阶段 | 模型倾向把较低层级的通过说成“已完成”，需要状态词和证据一一对应 |
| 保存后在新进程重新打开回读 | 往返（round-trip）持久化测试 | — |
| 集成按互斥文件集合分车道，最终车道唯一写共享文件 | 合并队列（merge queue）；按所有权分区合并 | 并行执行加快后，单一集成写入者成为新瓶颈 |
| 发布授权后冻结范围，新反馈进下一版 | 代码冻结、发布分支、发布列车（release train） | — |
| 自建测试资源末次使用后清理并回读 | 测试夹具的拆除（fixture teardown） | 代理容易“测完就走”，资源留在真实账号里 |

## 缺陷治理

| 本技能的规则 | 相近的成熟概念 | 多代理场景特有的地方 |
| --- | --- | --- |
| 止血线与类治理线并行 | 质量管理的“纠正”与“纠正措施”（CAPA）；ITIL 的事件管理与问题管理 | 以前人手少，只能修单点；并行代理让按类修复在成本上可行 |
| 试点通过即推广，盘点三态闭合才结束 | 绞杀者模式（strangler fig）的渐进迁移与迁移清单 | 代理会把“首批清空”报成“整类完成”，也会无限扩大范围，所以终点必须可检查 |
| 每类一个轻量棘轮：冻结存量位置，只许减少 | 静态检查的基线文件（如 PHPStan、detekt 的 baseline）；“棘轮”式质量门禁 | 按位置身份比较而不是按总数比较，防止删一处、加一处 |
| 先找成熟库，提议交用户决定 | 自研还是采用（build vs buy）；架构决策记录（ADR） | 代理受“最小改动”约束时，会默认自研 |

## 这张表没有覆盖的

以下几点在传统系统里由程序保证，在多代理场景下却常常只靠文字约束，也是我们最想交流的部分：

- **确认的真实性。** 传统消费者的 ack 由代码发出；模型可以“说”已处理而没有动作。
- **执行轮次的触发。** 消息投递到了，闲置代理也不一定会开始新的一轮。
- **状态词膨胀。** 模型倾向用更乐观的状态词描述阶段结果。
- **上下文断裂。** 接任者经常是新对话，只能从记录和工具状态恢复。

技能能写清这些要求，但写入成功、投递重试和自动唤醒仍然要宿主程序实现并验证，见[宿主适配说明](../skills/reliable-agent-dispatch/references/host-adaptation.md)。
