# 可靠的多代理调度

让每个已授权的用户结果持续有人负责，交付之后有下一步，阶段进展与真正完成分开报告。用户只对接主调度，经理负责本组日常接续。单一小任务由当前负责人直接闭环，不套管理层级。

## 与用户保持顺畅协作

1. **先回应，再查证。** 看到新消息先用一两句回应，再读记录或调用工具；已有信息和本次刷新事实分开。
2. **长任务保持可见。** 按双方约定简短更新新增结果、等待对象和下一检查节点，使用已有异步句柄与有界等待；不编造完成时间，不反复报相同状态。
3. **讨论期间保留原任务。** 新讨论不撤销已有目标，也不自动授权新方向的实施；用户明确暂停或改目标后更新安排。
4. **用用户结果汇报。** 第一行写能看到的结果和缺口；多项按“问题 / 当前结果 / 还差什么”。内部身份和日志放证据中。
5. **状态词对应事实。** 已派出、正在执行、源码候选、实际测试、集成、发布和用户验收分别核实，不把交付次数当完成数。
6. **信息只让用户解释一次。** 主调度将补充和纠正同步给相关经理，写回原任务；普通技术判断由负责人解决，业务取舍集中问用户。
7. **先接续，再完整汇报。** 核必要证据后真正恢复负责人、落实具体排队或说明外部缺口，随后确认交付；“收到”不能代替行动。

消息类型、暂停和交接见 [communication.md](references/communication.md)。

## 开始前确认能力与授权

先读当前项目规范、用户授权、已有任务记录和最近交接。技能本身不授予发布、部署、客户数据写入或删除权限；已有授权持续有效，不重复请批。只读、暂停及用户禁用的机器边界优先。

从本轮工具说明确认启动、通知、恢复、列状态、有界等待和持久交付的实际语义。通知不一定会唤醒闲置代理；配置保存不等于运行能力已生效。适配和小规模验证见 [host-adaptation.md](references/host-adaptation.md)。

接手时核实际代码目录、分支、未提交改动、代理状态及执行句柄，保留他人修改。复用原记录、原负责人和身份明确的已绿证据；旧台账的“执行中”不能证明仍在执行。原主调度活跃时先落实交接；同一任务只能有一个消费其交付的经理。

## 按任务设经理，日常接续在经理层完成

独立任务适合并行且工具允许时直接并行。按共同根因、文件写权和验收目标分组，实际出现管理积压再设经理；不按固定人数、技术栈或部门凑组。

| 角色 | 负责什么 |
| --- | --- |
| 主调度 | 用户唯一联系人；保留原始目标和全局优先级，复核业务疑问，裁决跨组冲突与权限边界 |
| 业务经理 | 意图初审、派单、核交付、必要审查、续派与验收；在已分配资源预算内直接安排下一步 |
| 资源统筹 | 一位现有经理兼任；统一看获准机器的实时负载和在途工作，防止容量被重复分配 |
| 执行者 | 完成本线定位、实现、相关验证和自建资源收尾，持续对同题负责 |
| 巡检 | 只查漏接和无人接续，先提醒直属经理；获得明确恢复权限时可恢复该经理，不另派业务或代确认 |

经理未结任务容量可配置，排队、待验证和外部等待也计入。原实践试用了每位经理最多十条；它是一次工作配置，不是通用上限，也不是必须凑满的数量。管理容量、代理工具名额、每机负载分别核算。按能力分配模型并按任务选择思考深度，服从用户分工，不固定品牌、版本或账号。

分层职责、资源分配与集成车道见 [manager-hierarchy.md](references/manager-hierarchy.md)。

## 反馈先分流，再决定怎么推进

- **明确缺陷：** 合法现有操作失败或违反既定承诺，按已有修复授权立即调查和修复。
- **新提案：** 新功能、行为变更或产品取舍，先查真实问题、已有入口、使用成本与影响；用户采纳前不实施、不承诺入版。
- **事实不明：** 先做不依赖决定的调查，经理带具体分歧报主调度；能依据已有决定裁决就直接处理，真有业务取舍才问用户。

结果项沿用原任务编号。经理先核原话、既定口径和实际场景；主调度复核疑问和关键节点，不重做每条执行日志。目标被收窄、拆分或部分排除时明确报告剩余项归谁，不能用局部技术通过替代原使用结果。

## 按依赖和写权派单

每条任务写清：**目标与证据、负责范围、禁止事项、完成标准**，并补实际工作目录、基线、执行者、直属经理、文件写权、指定机器和验证入口。使用 [templates.md](references/templates.md)，不要重抄全套规范。

- 写代码的车道使用独立工作树或等效隔离目录、分支和构建输出目录，全程复用本线输出。
- 同一文件同时只有一名写入负责人，独立工作树不构成双写许可。冲突交所属经理裁决，跨组冲突交主调度；其余读取、定位和测试继续。
- 同题的构建、验收和清理在原车道继续；换阶段或换机器不新建继任任务，也不通过关闭旧任务释放未完成责任。
- 未授权旁支只报告，不实施、不阻塞本题。同类入口治理只有在项目或用户已授权时才能按下一节开展。

## 缺陷分止血线与类治理线

在已获同类治理授权的项目中，经理收到缺陷就分别安排：

| 线 | 要交付的结果 |
| --- | --- |
| 止血线 | 最小修复、相关真实操作与清理，按正常版本交付；不等类治理或选库结论 |
| 类治理线 | 根因归类、盘点同模式入口、复用试点逐批迁移、轻量棘轮防回退；同一类共用一条治理主线 |

未获治理授权时，先提交简短类治理建议，止血工作继续。纯文案样式布局、数据配置或环境问题、查证没有第二处同模式的孤立错误可只修单点；最后一种要写搜索依据。验收时分开说“原问题是否修好”和“这一类是否关住”。

推广前明确范围和终点；在推广已获授权时，一类试点通过即可推进该类，不等其他类，也不反复请批。终点是**范围内旧入口全部有据可查地归为已迁移、现有能力足够或暂不做，并有已登记的棘轮守护**。暂不做须写原因和重新评估条件；待迁、待验和排队不能藏进暂不做。

棘轮只做轻静态扫描，每类一个，以单次一秒内为目标，不编译、不开目标程序。冻结存量位置，只许减少；新增旧写法就失败，不能用删除一处抵消另一处新增。静态守护不能代替实际行为验收。详见 [bug-by-class.md](references/bug-by-class.md)。

## 主动找成熟库和成熟做法

经理判断问题是否通用，可能有成熟解法就主动检索官方文档或维护中的项目。带候选、替代哪段自写逻辑、维护状态、许可证、体积与兼容代价交主调度，由用户决定；当前最小修复继续。

用户采用后按授权实施、锁定版本、验证目标运行环境与数据兼容，迁走被取代的重复逻辑。遵守当前项目的许可政策；许可不明先核实，不把依赖包名当许可证明，也不以“少依赖”默认选择自研。提议模板与评估边界见 [mature-libraries.md](references/mature-libraries.md)。

## 交付、接续与确认

执行者先保存本线结果，再通知直属经理，包含阶段、候选和产物身份、证据、剩余动作及清理情况。工具接受启动或恢复后才报告“已派出”；执行状态另核。

经理核一次直接差异与必要证据，普通改动按项目约定做一轮审查，发现本次阻塞再补查。由非实现者独立审查；同模板推广可按已批准规则每类每批抽样，新逻辑或新合同仍单独审查。

剩余工作按事实处置后再确认交付：

- **可执行：** 实际恢复原负责人或明确继任者，保留工具回执。
- **内部排队：** 写明负责人、下一步、所等资源或产物、提供者与恢复条件；条件到位实际启动，不冒称外部阻塞。
- **外部等待：** 写清缺什么、谁提供、是否已提出请求、影响步骤及到位后由谁恢复；其他已授权步骤继续。
- **目标达成：** 约定结果、必要审查和清理均齐，才能结项。阶段交付或确认不等于整项目标完成。

复用现有队列或任务记录，不为小任务新增服务。已确认阶段后又有交付到达，以新事件身份处理，不能覆盖未消费交付或删除记录清绿。

## 集成与发布保持明确范围

候选较多时，按互斥文件集合分集成车道，各自组合和验证；最终集成车道唯一写共享清单、依赖锁文件及生成产物，并做组合验收，不重审全部已验候选。单一文件写入规则始终有效。

发布获授权后盘点当时已有候选与交付，记录实际身份并冻结范围。冻结后的新反馈照常按授权修复，进入后续版本；只有用户明确加项或本版自身引入的回归才调整本版，并记录新冻结。其他车道继续推进，不能边打包边改冻结源码。集成允许不等于公开发布允许。

## 验收用户结果并结束本轮

核候选源码、实际运行程序、真实输入和输出属于同一交付。源码、构建、所需平台操作、集成、发布和用户验收分别报告，只要求与本题有关的层级。保存任务需要新进程重新打开回读；自造场景不冒充原案通过。真实链失败交原负责人最小追查并重走，缺外部输入只暂停依赖步骤。

经理结束前核本组任务记录、当前代理状态和漏接检查；主调度核经理摘要、当前经理与巡检状态及异常，不逐条重读全体执行者。工具结束但记录仍运行、交付未确认或余项无人负责时，处理或明确排队；新增交付消费后再核。

自建测试资源记录精确归属和最后使用者，末次使用后按已有授权清理并回读确认；停止自有进程、恢复现场。测试清理失败保留欠账。内部源码和证据保留，不能把此规则扩大为永久删除他人资产。

源码候选形成后停止无关扩展和重复审查，本题必要验收继续。真实终点满足就结束，不为保持代理活跃造任务。未验证的后台唤醒不能承诺；交接写清检查点、负责人与恢复触发，预算耗尽或代理退出不能写成目标达成。
