# 可靠的多代理调度

让每个已授权的用户结果持续有人负责：同一线程从定位追到最终验收，用户不在时系统也能自己跑下去。主调度只对接用户；补位、盯卡死、分配机器、修已知故障，尽量交给脚本。

本技能执行[第三版](../../docs/scripts-and-self-heal.md)，协调结构的来由见[第二版](../../docs/coordination-structure.md)。本仓库不附带队列服务、状态脚本或机器工具，[scripts.md](references/scripts.md) 只写这些脚本该满足的合同，实现靠你所用的工具。使用前先核当前宿主的能力；本项目的上下文、缓存和成本经验，不能直接当成其他环境的结论。

## 开始前确认能力、原记录与授权

- 读当前项目规范、已有授权、原任务记录和最近交接。发布、云端部署、客户和公开数据写入、永久删除、凭据及权限变化须有明确授权；已有授权持续有效，不重复请批。只读、暂停和用户禁用机器的边界优先。
- 核实际代码目录、基线、已有改动、执行者状态及运行句柄，保留他人修改。复用原记录、原负责人和证明范围明确的已通过证据；旧台账写着“执行中”不证明仍在执行。
- 核启动、通知、恢复、列状态、有界等待和持久交付的实际语义，见 [host-adaptation.md](references/host-adaptation.md)。消息送达不等于闲置线程已恢复，配置保存不等于能力生效。

## 门槛要能指到用户原话

- 流程里每加一道门槛（交接、顺位、授权链、来源证明、硬截止、额外审查、登记回执、拒绝启动的守卫），和产品里加路障一样，须单独取得用户批准。没批准的不加。
- 现有门槛对不到用户原话、也不护着硬边界（客户或公开数据、发版、凭据、真实账号、权限、永久删除、关机注销）的，删掉或降成只记录、不阻塞。定期按这两个问题过一遍。
- 写规矩时，“让谁多干”不要写成“别人不许干”。默认某件事做不到之前，先实际试一次。例如同一个测试账号能不能两处同时登录，试过再定。

## 能写成脚本的规矩写成脚本

- 条文在长对话里触发不稳定。能检查的规矩写进命令本身：缺了必填项就拒收；该做没做，定时检查就非零退出报红。条文和脚本冲突时以脚本为准，改规矩先改脚本和测试。
- 新角色出现之前，先问它的活能不能写成脚本。补位、数卡死、分配机器、修已知故障都已有脚本合同，见 [scripts.md](references/scripts.md)。

## 协调结构

| 角色 | 职责 |
| --- | --- |
| 执行者 | 一个独立问题一个，同一线程完成定位、修复、测试、必要构建、真实验收、保存回读、清理和候选登记。自己向分配脚本要机器，自己等构建 |
| 主调度 | 用户唯一联系人。转达用户原话、反馈、决定和授权；待决定的事立即呈现，答复写回原记录。用户问进度时先报结果清单（修好、已改待验、未解决、需求各几项），再逐项写“问题／结果／还差什么”。不派执行者、不读执行过程 |
| 补位员 | 只有一层。每轮跑补位脚本，照它给的全部可开工项开工：原执行者还在就先唤回，接不上再开新的；开工单原样交给执行者，不改写、不转述。不对接用户、不审查、不读过程，只在两条线真撞上时裁决 |
| 巡检 | 每小时读卡死脚本的报告，判断根子和该谁动，交主调度并记摩擦账本。只建议，不动手 |
| 公共设施 | 机器分配脚本；集成、发版各由一个执行者做到终点；独立审查只用于高风险改动；界面由适合且获准的模型按需协作 |

多个独立问题在授权和工具能力内并行，不按业务凑组。有可做的步骤就派，人数只作统计。机器不足时，报告资源缺口和受影响的任务数。各角色共用实际的代理名额，机器容量另查，详见 [manager-hierarchy.md](references/manager-hierarchy.md)。

## 一个问题一个线程，从定位做到验收

- 首次派单写清**用户目标与直接证据、负责范围、禁止事项、最终验收标准**，补实际目录、基线、机器边界和现成验证入口。验收覆盖本题必要的真实入口、保存后新进程回读、自建资源清理和最终回执，不拆成阶段派单，见 [templates.md](references/templates.md)。
- 执行者到下一阶段直接继续，等机器或构建时保留句柄，用宿主支持的方式等待。只在三种情况交付：需要用户决定；需要别人的产物或冲突裁决；做完。交付时把结果、证据和剩余项一次说清。
- 继续做就用真正的恢复工具启动原线程。阶段结束、上下文变长、发生压缩或暂时等待，都不是换人的理由；只有工具证实原线程无法恢复，才登记继任。继任前先核在途进程，只读最后一份最小回执和开工必需的材料。
- 普通改动由实现者自审，加直接相关测试，一轮就停。权限、删除覆盖、报价或生产输出、不可逆迁移、云端部署、发版这类高风险改动，由非实现者独立审查一次。不给每个候选另配审查线程。

## 反馈只用四个状态

| 状态 | 必填内容（缺了脚本拒收） | 离开条件 |
| --- | --- | --- |
| 处理中 | 一句人话标题、实际执行者；收到 15 分钟仍无人负责就报红 | 需要用户决定、候选修好或结案 |
| 等你定 | 问题、推荐、推荐怎么做、不选推荐的代价，以及实际呈现记录 | 用户答复；普通决定呈现后 3 分钟无回复按推荐办 |
| 待发版 | 候选身份、提交和验证层级 | 获准发布，并且公开回读通过 |
| 已完成 | 已发版修复（版本加发布回执）/ 不是缺陷已答复 / 不做 / 并入原问题 | 新证据到位或用户改主意时重开 |

- 没有“排队”和“等外部”状态。等机器、等构建仍是处理中，依赖、提供者和恢复条件写在同一条记录里。
- 缺证据先找本地原件；仍缺，就在证据请求库里登记缺什么、向谁要、查过哪里，附一段可直接发送的请求文案。车道用现有材料完成能做的部分，注明“原案未覆盖”；证据到位后重开原问题补验。
- **普通决定呈现后 3 分钟未回复，记“未答复，按推荐”并执行。发布、云端部署、客户和公开数据写入、永久删除、凭据及权限变化不适用，缺明确授权永远不自动放行；这类硬审批没答复时定期汇总提醒。** 未呈现的不能开始计时；用户事后推翻普通推荐，就照新决定执行。
- 通知要真实送到才算送到：待发箱逐条确认已发出，超过 5 分钟没发出就报红。用户点名要的结果，有了就主动报。

## 机器按实时压力分配

- 谁要机器谁调用分配脚本，按它回的机器和并行数直接开工，做完归还。不设资源经理，不等人批份额。
- **放行看实时压力，不看账面预约。** Mac 内存压力不是“严重”就放（系统会自己压缩）；Windows 承诺内存低于 95% 就放（承诺内存是硬上限）。压力未知就换一台。账面预约只用来在几台机器间排先后，不用来拒绝。
- **平时不排队。** 能放的机器里有一台在线内就当场给，都越线才排队；不为任何等待项预留整台机器。叫醒两次都没来领的等待项，移出名单并通知本人。
- **预约按实测纠正。** 开跑满 10 分钟后，改成最近 10 分钟峰值的 1.3 倍，最少 0.5G，涨了也跟着调；空出来的内存马上叫醒等待的人。发版预约同样纠正，只在排先后和退回时保留优先。
- **持续严重过载才退回。** Mac 严重、或 Windows 承诺内存 ≥ 97%，持续 2 分钟：先暂停后台活，再一次退回一个最新放进去的普通编译或测试，按原排队时间回池并通知本人。界面实测最后退，退之前先让它保存现场。
- 平台无关的编译和测试申请“哪个平台都行”。用户正在用的机器不选；用户的屏幕不拿来做界面实测。同一台机器上点界面一次只给一条线。
- 机器闲着、却有车道在等，定时检查报红。

## 已知故障由自愈手册直接修

- 自愈脚本随定时机器检查运行。每条修复写清三件事：怎么认出来、怎么修、怎么算修好了。同一问题 6 小时内修 3 次还不好，报红交主调度查根子。
- 主调度或巡检查清一个新故障的根子后，可以自己往手册加规则。新规则先只记录、不动手，观察满 24 小时；再用事故时刻和正常时刻各回放一次，事故命中、正常不命中、没有误报，才转为执行。手册校验时直接拒收删除、关机注销、停别人进程、对外写、凭据、提权这几类动作。
- **拦不住模型写出失控的脚本，就把兜底做在本机。** 每台机器装一个常驻看门狗，每十几秒查一次，只认“我们的”进程：远程会话起的、我们的计划任务起的、分配脚本登记过的。超线就在本机直接结束、记日志、通知负责人，用户的应用一律不碰。同一负责人一天被结束两次以上，交主调度查根子。条件允许时，用系统的进程组内存上限（如 Windows 作业对象、Linux cgroups）做第二层。

## 摩擦当轮记账

- 目标是无人值守持续运行。以下四种都算摩擦：要用户本人介入；有活却空等超过 15 分钟；同类手工步骤第二次出现；流程让已有产出作废。
- 碰到的人当轮在摩擦账本里追加一行：现象、代价、根因、怎么消掉、状态。优先写成脚本检查或自动处理，规矩文字只留指针；写不成脚本的说明原因。复发就把状态改回“部分”，不新开重复行。
- 关键路径卡住超过 15 分钟，只能三选一：修好工具重试；换获准的机器或路径；经主调度马上问用户。命令错误或工具调用失败，不能自动算外部欠账。

## 同一文件可以多线并改

各线用独立的工作树、分支和独占的构建目录，全程复用本线的输出。默认乐观合并：先合者先进，后合者在最新基线上变基；解冲突时保留已合入的内容，不整块采用自己这一边。不做无关的整文件格式化、大段搬动和批量重命名。确实不能并改的少数热点单独登记，这张清单默认是空的。

## 业务判断由处理问题的执行者完成

- 明确的缺陷，按已有授权做最小修复。新功能、行为变化或产品取舍，先核真实问题、已有入口、用户成本与影响，带推荐交主调度。未授权的旁支只报告，不实施、不阻塞。
- 修完记一行根因类别、同模式入口、守护为什么没抓到。用户批准某一类后，才开一个执行者做该类治理，见 [bug-by-class.md](references/bug-by-class.md)。
- 执行者主动检索成熟库、官方做法和行业通用解法，交主调度向用户提议，当前修复不等选型。**借别人的工作方法，先列前提、对照实际，在小批车道试跑一两天，端到端数字变好才推广，变差撤回。** 见 [mature-libraries.md](references/mature-libraries.md)。

## 集成、发布与结果验收

- 集成、发版各由一个执行者追到终点。发版是晋升已验证的候选：编译、测试和冒烟在冻结前做完；冻结后只做签名或加密、对同一个包冒烟、公开回读，不重新编译。冻结之后新来的归下一版。
- 发版执行者遇到要等人决定的事，不停下来问：把该项移出本版，走不可逆程度最低的路继续发，发完逐条告诉用户跳过了什么。不跳过的只有四样：包来自冻结源码且身份核对通过；本版改动直接造成数据丢失、越权或错误生产输出；公开回读必须通过；凭据安全。
- 源码、构建、平台真实操作、集成、发布和用户验收是不同的层级，分别说清到了哪一层。保存相关的问题，用新进程重新打开回读；自造的场景不能冒充原案。
- 自建资源按已有授权清理，停止自有进程并恢复现场，不清他人资产。

## 每天看几个数

- 每个问题用了几个线程（目标 1–2 个）、中途来回几次（不超过 3 次）、管理类 token 占比（我们的可接受线约 30%）。
- 门槛减法、分配规则这类改动，跑满一天后按同样口径和改动前比：各类卡点的消息数、同时在跑的任务数、平均排队时间、因过载退回和被看门狗结束的次数。
- 换环境要先立基线，不承诺普适效果。
