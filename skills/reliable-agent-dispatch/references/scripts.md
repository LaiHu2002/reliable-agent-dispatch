# 脚本合同：把规矩和协调动作交给程序

本仓库不附带实现。下面每一项，写的是我们实际在用的脚本该满足什么。你可以用自己的语言和工具实现。

共同要求：

- 只读的查询不改任何记录。
- 会改记录的命令，缺必填项就拒收，并说清缺什么。
- 定时检查发现问题就非零退出，输出一行人能看懂的原因。
- 不为计时另起常驻服务。复用已有的定时检查；每条状态命令执行时，也顺手检查一遍超时。

## 1. 反馈状态机

| 命令 | 必须做到 |
| --- | --- |
| 建条目 | 一句人话标题；用户点名的要标出来 |
| 改状态 | 只允许“处理中 / 等你定 / 待发版 / 已完成”，各自的必填项缺一项就拒收（见技能正文） |
| 问用户 | 必须注明是普通决定还是硬审批。普通决定实际呈现后 3 分钟没回，自动记“未答复，按推荐”；硬审批永不自动放行，定期汇总提醒 |
| 已发版 | 必须附发布回执文件，回执里要写着这个版本号 |
| 登记缺证据 | 必须写已经用现有材料试过什么；区分要发给外部的和内部找人的 |
| 待发箱 | 只列出、不改记录，每条带编号；真实发出后逐条确认。超过 5 分钟没确认就报红。只对“问用户”和用户点名的结果按超时报红；看门狗结束任务、资源预约之类的记录型通知不进待发箱，每天在近况里汇总一行同一类通知合成一行，要人动手的报红排前面（我们吃过亏：一次检查报了 74 条红，真问题只有十来条；改完同一份数据是 26 条）。 |
| 汇报数字 | 从逐条结果统计。只有已发版的修复算“修好”；修好待发版单列；答复、不做、并入不算修好 |
| 进度表 | 由脚本生成，人和主调度都看这一张 |

## 2. 补位

- 输入：状态机里所有未结的条目，加上各执行者最近的活动。
- 输出：全部可开工项，按原负责人分组；每项附一张开工单，只放用户原话、原件路径和编号。
- 定时任务照单开工：原负责人还活着就先唤回，接不上再新开；开工单原样转交，不改写、不转述。唤回后核对方实际开了新的执行回合，消息发出不算。
- 只把“近期活跃人数”当统计用，不设上限。

## 3. 卡死报告

增量读各执行者的会话记录，数出以下几种情况，写成一份报告：

- 说了接下来要做什么，之后 2 小时没下文；
- 最近连续 3 次失败；
- 两小时内两条以上的线卡在同一类（启动没就绪、登录、前台、崩溃、内存保护、盘满、等机器、等用户、构建失败）；
- 性能类的线 4 小时没出耗时数字；
- 有线说在等机器，同时却有机器闲着。

关键词表放在配置里，可以随时改。巡检每小时只读这份报告，加上被点名车道最近的几条消息。

## 4. 机器分配

- `pick`：输入任务类型（编译 / 测试 / 界面实测）、平台（某个平台，或“哪个平台都行”）、申请人、可选的内存估计；输出给哪台机器、建议几路并行，或者为什么现在没有。
- 放行按实时压力，规则见技能正文。预约只用来排先后，不用来拒绝。
- 没给申请人指定内存时，用同类任务历史实测的中位数 × 1.2。申请明显超过历史 p90 的，放行后照样按实测纠正。
- 预约开跑满 10 分钟按实测纠正；15 分钟内一直没有进程绑定的空预约自动收回；叫醒两次都没来领的等待项移出名单。每一次纠正、收回、叫醒、退回都写日志：前后各多少、实测峰值、叫醒了谁。
- 用户登记在用的机器不选。平台无关的任务申请成某个具体平台时，照常分配，结果里提示一句“这类活可以用‘哪个平台都行’”。
- 远程到 Windows 时只复用一条长连接。每新开一次连接都可能漏一个登录会话，攒多了只能重启。

## 5. 自愈手册

- 内置条目：每条写清“怎么认出来 → 怎么修 → 怎么算修好”。
- 可扩展条目：报红字样（正则）→ 修复脚本，或者给主调度的一组固定步骤。
- 新条目的生命周期：先只记录、不动手，观察满 24 小时 → 用事故时刻和正常时刻各回放一次 → 确认无误报 → 转为执行。
- 校验：修复脚本里出现删除、关机注销、停别人进程、对外写、凭据、提权的，拒收。
- 同一问题 6 小时内修 3 次还不好，报红上交。

## 6. 本机看门狗

- 每台机器一个，本机常驻，每 15 秒左右查一次，不依赖远程连接。
- 只认“我们的”进程：远程会话的子进程、我们的计划任务起的、分配脚本登记过的进程树。用户应用不碰。
- 单进程超线就结束。按类型设线：脚本宿主类（shell、Python、Node 等）线最低，编译器和测试程序其次，界面程序再其次。
- 整机快顶满，持续几十秒以上：结束“我们的”进程里最大的一个，一次一个。
- 每次结束都写日志：进程、命令行摘要、上级链、峰值、按哪条规则、当时整机内存。能对上负责人的，通知负责人。
- 看门狗自身要有内存上限，挂了能被系统自动拉起。
- 有条件就加第二层：用操作系统给进程组设内存硬上限（Windows 作业对象、Linux cgroups）。

## 7. 摩擦账本

一张追加写的表，每行：日期、现象、代价、根因、怎么消掉、状态（已做 / 部分 / 未做）。复发就改回“部分”，不新开重复行。每天的汇报里提一句新增了几行、消掉了几行。

## 8. 已发认定

- 输入：所有待发版条目的修复提交；正式版列表（每版的发布回执，以及打包所用的源码提交）。
- 修复提交是某个正式版的祖先，并且这段改动在该版和最新正式版里仍能反向对上，算随该版发出。
- 否则取该修复新增的产品代码行（不含测试、文档、配置类文件），在正式版源码同一文件里查找：≥90% 且每个文件都有命中，算已发；50%–90% 标“疑似”，交原负责人核；其余仍是待发。
- 确定的由定时检查自动补标为已发版（带版本和回执）；按“修复提交 + 正式版分支头”缓存，没有新版本就不重算。
- 回测要求：拿人工逐条核过的一批去比，没发的不能被认成已发。

## 9. 对账与近况

- 每小时一次：待发版交给已发认定；处理中两小时没动静的唤回原负责人或换人；等用户定、卡在用户身上的，核实是不是真的还要等；证据请求里材料已到的，重开原条目。
- 对完生成一页近况：这一小时（问题 → 结果）、在做的（按领域分，写条数和最重要几条到哪一步）、卡住的（卡在用户身上的写清要用户做什么）、下一版（几条、预计时间、卡点）。数字逐条计算，和汇报口径一致；不写内部代号。

## 10. 发版报红

- 同一阶段连续失败 3 次且最近一次在 3 小时内，报红，要求换办法或撤项。
- 能并行的阶段却串行跑了、失败阶段没人重跑，报红。
- 近 24 小时发版类线程的 token，超过“公开版本数 × 每版预算”就报红，并列出最费的三个线程及其调用次数。
- 以上都只报红、不拦人。
