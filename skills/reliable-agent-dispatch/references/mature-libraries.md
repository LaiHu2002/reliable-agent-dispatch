# 经理主动找成熟库和成熟做法

当问题在行业中普遍存在，经理应主动判断有没有维护中的库或成熟项目可借鉴。把合适的一部分抽象交给成熟实现，可以减少自写代码和重复处理边界情况；采用是否值得仍由真实兼容效果判断。

## 检索与提议

先查当前已有依赖和能力，再检索候选的官方文档、源仓库、发布记录与许可文件。维护状态和运行环境支持可能变化，提交提议时记录核查日期和实际版本。包名、热度或一次安装成功都不足以证明成熟或适合。

在原任务里写一份短提议，不另建选型平台：

```text
问题类别：当前反复出现的错误机制
候选：库或大型项目的做法，直接官方来源，核查日期与版本
替代范围：准备移走哪段重复自写逻辑，保留哪些必要适配
成熟度：维护、发布与实际使用证据；仍不确定什么
许可：直接和传递依赖的实际许可，项目是否允许，须保留什么声明
成本：新增依赖、构建产物体积、启动与运行开销、目标环境支持
兼容：数据读写、现有调用合同、支持版本与部署入口
推荐：采用 / 先试一条链 / 不采用，理由及不选推荐的代价
验收与退出：真实试点、迁移批次、移除旧实现和失败时停止条件
```

经理交主调度，由主调度主动向用户讲清建议。明确采用即为实施授权，不再用一般“禁止扩范围”规则阻挡已批准依赖；新增行为、外部资产及其他硬边界仍按原授权处理。

## 当前修复不等选型

最小修复与候选调研并行。不要为了选到理论上最好的库拖延用户当前结果，也不要以“最小改动”“少依赖”为由从不查现成解法。

采用前已有具体用户授权就复用，不重复请批。没有候选也可有据地结论“不接库”，例如现有能力已经足够、实际瓶颈不在这一层或兼容代价过大；不能把没检索说成没有成熟办法。

## 按目标环境验证

- 库放在本项目拥有该业务责任的层，不能因容易接入而建立第二个事实来源。
- 按项目现有许可政策核实际依赖树。原实践默认选择 MIT、Apache-2.0 等许可兼容的方案；别的项目以自己的政策为准。许可不允许引入的实现可研究思路，不复制受限代码；拿不准的许可另核。
- 锁定版本，复用现有构建链，核真实交付产物而非仅开发环境可运行。嵌入式网页、受限浏览器或桌面宿主尤其需要实机核对。
- 对比包体积、启动和直接相关动作成本。性能对比使用同机、同输入、匹配程序和正常优先级，报告真实波动，不只取最好一轮。
- 保持已承诺的数据格式和支持版本读写。未经授权不顺带迁移存储格式；验证范围来自当前项目合同，不把原项目的兼容版本数量强加给其他人。

## 采用以后完成替换

先接一条真实链，按已授权范围逐批迁移。生成的合同或构建产物必须被实际程序消费；“依赖已经安装”不算接入完成。

迁移期间可按明确批次保留尚未迁的路径，写清临时并存范围、负责人和退出条件。每批接通后删去被替代的重复逻辑，最终不长期保留两套规则。必要宿主适配保留，但不能悄悄回到旧业务实现掩盖新库失败。

试点失败时保留原因、停止推广并恢复可用路径；选择不用某库不等于这类问题已经治理完成。是否修好原缺陷、类盘点是否闭合、依赖是否已进入正式交付分别报告。
