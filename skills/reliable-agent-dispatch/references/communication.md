# 顾问与人的协作

本文件来自负责人实际使用中的纠正，以及其请 Claude 整理的协作总结。目标是让用户掌握结果、表达新想法和作必要决定，同时让已经授权的工作持续有人负责。

第五版起没有主调度。用户跟顾问（自己开的一个对话）讨论、看进度、交代新任务；顾问把任务登记成条目，派单脚本每轮照可开工项启动或恢复执行者，开工单原样传递。执行者的结论直接写回原反馈条目。业务判断与最终用户结果由原执行者核对，顾问不读执行过程。

## 不同消息怎样接

| 用户消息 | 第一时间回应 | 随后的实际动作 |
| --- | --- | --- |
| 问进度 | 先给最近已知结果；需刷新时明确说正在核实 | 读当前任务、交付与执行状态，接上可执行余项，再修正汇报 |
| 讨论新想法 | 回应想法本身，弄清讨论范围 | 对新想法保持已授权范围，同时保留原任务；结束回复前检查原队列 |
| 补充参数、模型或决定 | 说明它影响哪项问题、哪一步 | 同步原负责人并更新已有记录；负责人闲置时用实际恢复工具接续 |
| 纠正理解 | 用一句话说明修正后的理解 | 更新派单或本轮获准修改的规则，不让用户到每条执行线重复解释 |
| 问为何没回复、是否卡住 | 讲已知事实和待核内容 | 查实际执行与未处理交付，处理后说明原因和下一可观察结果 |
| 明确暂停或取消 | 先确认停止接新活的范围 | 按任务要求保存检查点、释放自有现场，核实后再报告已停止 |
| 收回某台机器 | 确认该机停止接新任务 | 登记机器在用，通知相关执行者，用现成脚本核获准机器并保留原线程继续；其他获准机器继续 |

## 短答之后还要推进

“先回一句”保持沟通。短答之后继续读取、核实和执行，不能把短答当成任务结束。

持续工作期间按用户偏好约定更新节奏。普通进度不推送，留在账本里，用户问时由顾问读；派单和提醒按脚本处理，推进员只在脚本点名时出场。只有硬卡点（硬审批、真实缺材料）用不会自动消失的提醒打扰用户。没有新结果就讲等待对象和下一检查节点，不为汇报反复查询工具。

长编译和测试优先保留已有异步句柄及日志，使用工具允许的有界等待。能否及时接到新消息按实际工具能力说明，不为改善回应再搭一套后台服务，也不重复启动仍在运行的任务。

## 汇报到用户能作判断

第一句给结果，例如：“导出列已修，相关测试通过；目标程序里的实际导出还没验证。”

需要多项对齐时，按用户操作命名：

| 问题 | 当前结果 | 还差什么 |
| --- | --- | --- |
| 导出缺少单位列 | 源码修复、相关测试通过 | 指定平台实际导出，由原负责人继续 |

任务分支、进程、运行程序身份和原始日志放证据，正文避免堆内部代号。普通一句追问直接回答，不要求每次填满表格。承诺时间之前先确认依据；估计有变化及时更正。

“已派出”需要启动回执；“正在执行”需要当前执行事实；源码、构建、实际操作、发布和用户验收各有证据。用户尚未验收时不能代其宣布通过。

## 把讨论、决策和执行接起来

用户可以一边让代理执行，一边与顾问讨论。讨论新方向时，不自动启动新方向的实现，也不默认撤销原来已经授权的目标。用户明确调整优先级、暂停或替换目标后，再更新原记录并同步负责人。

执行者核原话、现场和既有产品口径，解决普通技术安排；真正可能改变用户结果的分歧直接登记为待用户决定，写清问题、推荐、代价及影响；其他独立工作继续。新提案先评估，不能把“标成缺陷”当作采纳证据。普通决定由脚本直接按推荐办并记录；云端部署、客户和公开数据写入、永久删除、凭据、权限变化和关机注销没有明确授权绝不自动放行，由提醒框请用户处理。

补充信息归入原问题；运行中的负责人及时收到必要更新，闲置负责人使用本轮真正能启动它的工具恢复。“已通知”和“已恢复执行”分别核实。

回复用户以前，先落实本次必要的原线程恢复、依赖接续或责任转交。原任务尚有后续时，不以一段完整总结代替继续工作；没有独立后续的任务允许结束，不制造额外工作。

派单脚本列出并派出全部可开工项，缺字段或提醒未弹出由状态检查报红；需要判断的阻塞由脚本交推进员。目标缩小、拆分或部分排除时明确交代未达成结果项的归属；队列正常和阶段关闭不能替代原用户目标完成。

交接顶部只保留一份简短当前摘要，历史移入已有历史记录；留下原目标、各负责人、未消费交付、机器占用、剩余动作与恢复触发。接任前核旧执行者是否仍在执行，落实单一消费，不能把新对话当作旧任务已停止。

结束前检查发生在相应角色实际运行时。子代理随后才交付的场景，还需要已经验证的通知、巡检或恢复能力；技能文字本身不能开启新的执行轮次。
